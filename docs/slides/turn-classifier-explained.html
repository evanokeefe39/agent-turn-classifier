What is a "turn"?

One message from you that starts a piece of work. You write "add the salesforce source, first time connecting it" — that is one turn. Everything the agent does in response belongs to that turn. This deck is about labelling those turns.

The transcripts are already on disk, in an open format. Nothing needs to be instrumented. The value is sitting there unread — because reading it means someone has to say, of every one of those 4,459 turns, what kind of work was that?

ComplicationThe obvious way to label them does not scale

You want every turn tagged with a workflow — "connect a new source", "fix bad data", "refactor a slow job". The taxonomy is open-ended: the shipped example defines six workflows across four domains, and a real deployment declares its own.

Option A — keyword matching

if "refactor" in text or "slow" in text: ...

Breaks immediately.

"it's getting hard to maintain" is a refactor. "make this faster" is a refactor. Neither says "refactor". A regex cannot read intent, and one bad pattern silently mislabels thousands of rows.

vs

Option B — ask a large language model

Send all 4,459 turns to GPT-class API, get a label back.

Works — but scaling hurts.

Cost, latency, rate limits, and a hard dependency: your historical data now needs a live API call to be readable. Re-run the corpus and the labels can change.

The tension we actually have

We want the accuracy of a large model, but the speed, cost and independence of a local script. Those have felt like a trade-off. The rest of this deck is how we break it.

ResolutionUse the big model to teach a small one

This is the core trick, and it is one idea:

TEACHER

Big model labels

Expensive, slow, brilliant. Sends each turn to a frontier LLM and gets a workflow back.

STUDENT

Small model learns

Trained to copy the teacher's behaviour. Tiny, fast, CPU-only — no API at prediction time.

RESULT

Ship the student

You paid once, offline. Now labelling 4,459 turns takes seconds, for free, forever.

"Distillation" — the industry term

Training a small model to imitate a large one. The large one is the teacher; the small one is the student. The teacher never runs again once training is done. Think of it as: the teacher writes the answers, the student learns to produce them alone.

"Inference" — what you do with a trained model

Using a model to get a prediction. Training is the learning phase; inference is every time you ask it something afterwards. The whole point here is that inference needs no API call — it runs as ordinary Python on your machine.

Key conceptsThe five things you need to know

1 · Text becomes numbers (embeddings)

A turn like "wire up the amplitude feed" is converted into a list of ~400 numbers that captures its meaning. Similar work produces similar numbers. This is the only "magic" step, and it is a standard off-the-shelf component.

2 · A tiny classifier on top

Once turns are numbers, labelling them is ordinary supervised learning — the same shape as logistic regression you may have used. It learns a boundary between "connect a source" and "fix bad data".

3 · A held-out set (the exam)

You never test a model on what it trained on — it would just be reciting. Data is split: the model studies one part, is graded on another it has never seen.

4 · Splitting by session, not by turn

Turns inside one session are all about the same thing. Split them randomly and near-identical turns land on both sides — the model looks brilliant because it has effectively seen the exam. So we split so that whole sessions go to one side only.

5 · Macro-F1 — the score

A single number for "how good were the labels", from 0 to 1. Higher is better. It is the score we measure everything else against.

6 · A "floor" you must not cross

Some turns are not work at all — "thanks", a stray question. The model must be allowed to say "not a work turn" rather than force a wrong label onto it.

Concept detailMacro-F1, without the maths

Why not just use "percentage correct"? Because that measure lies when one class dominates.

Accuracy (percentage correct)

If 90% of turns are "add a source", a model that always says "add a source" scores 90% and has learned nothing.

Rewards laziness.

vs

Macro-F1

Score each workflow separately, then average the scores equally. A rare workflow counts as much as a common one.

A model must be good at everything.

F1 — the jargon

A blend of two questions: of the turns I labelled "refactor", how many really were? (precision) and of the turns that really were refactors, how many did I find? (recall). F1 combines them into one number, so you cannot cheat by guessing one class constantly. Macro means we average that number across classes rather than across rows.

"Class" / "label space"

The set of answers the model may choose from. Here each class is one workflow id. The model picks exactly one per turn — it cannot answer "both" or "unsure". Deciding what belongs in that set is a design decision, not a technical one.

Six steps, each producing a file you can inspect. Nothing is hidden inside a black box.

"Encoder" — the term

The component that turns text into those ~400 numbers. It is trained separately and reused. In our design the same encoder is exported once and shared across every dimension we classify — you do not pay for it twice.

MechanismHow we know the number is real

A high score is easy to fake by accident. These four guards are what make a score believable.

Session-disjoint folds

The exam sessions are excluded from training entirely. We assert this on the folds actually used, not on our intention.

Without it, a template-like corpus scores ~1.0 and means nothing.

Same population for both

Teacher and student are scored over the same set of turns. If the teacher is graded over 100 turns and the student over 72, the comparison is fiction.

Counts must add up

We assert that skips + unplaceable + scored exactly equals the total. An arithmetic identity — but it is how we caught real bugs.

Loud failure, never silent

If a check cannot run, it says so. A test that passes because it matched nothing is worse than a test that fails.

This is the part most people skip

An evaluation framework is not bureaucracy. Every one of these four guards caught a real bug in our own code — a denominator that counted different populations, a label that was trainable when it should not have been, and a score that was comparing the model against its own teacher rather than the truth.

NuanceWhere this gets subtle — and where we were wrong

Three findings from our own measurements. Two corrected our design; one is still open. We are showing them because they change the plan.

Finding 1

A "ceiling" that is not a ceiling

The plan compares the student against the teacher's score and asks "are you within 0.10?". But if the teacher is worse than the student, that test passes automatically and measures nothing. Our fixture hit exactly this: student 0.98 against a teacher of 0.71. The gate said "pass". It should not have.

Finding 2

The score kept moving — and it was not leakage

Our score was suspiciously high, so we assumed data was leaking across the split. We measured it properly: it was not. Scored the same way both times, the model got 0.98 either way, and all 72 nearest neighbours were same-workflow. The truth was simpler — the test fixture was just too easy.

Finding 3

Real data did not look like we assumed

Our own adapter, written from the existing pipeline's queries, read the wrong fields — the schema nests them differently. It silently labelled every single turn as "other". It looked like it worked. It had never worked.

The pattern worth remembering

Every one of these failed quietly. None raised an error. They produced plausible numbers. That is why we build assertions before we trust a metric — and why we would rather report "this cannot be measured" than a number that keeps changing.

NuanceWhat we are deliberately not doing

The teacher is not the truth

We train on what a large model said, then grade the student against human-confirmed labels. If the teacher is wrong, the student inherits it — so we measure the teacher's own accuracy rather than assuming it.

We do not tune the fixture to look good

The synthetic test data is there to prove the plumbing works. When it proved too easy to measure quality, we said so in the README instead of editing it until the number looked respectable.

We do not guess at intent

When a turn does not fit any declared workflow, the model returns "unplaceable" rather than forcing the nearest match. Those cases are then reviewed and either promoted to a real workflow or discarded.

We do not hide the gaps

Where a claim is unverified — the training run has never executed end to end, for example — the file says so plainly. A stated unknown is useful; a silent assumption is a defect waiting to surface.

Expected impactWhat this changes day to day

Before

To answer "what have I actually been working on?", you read logs by hand or send them to an API. Costly, slow, and the answer changes each time you re-run it.

After

One command labels every turn. Runs in seconds on a CPU. Offline. Identical results every run. Raw transcripts untouched throughout.

Concretely

  • You can see your own work patterns — time by workflow, which projects needed the most cleanup, where you got interrupted.
  • It works on a laptop — no GPU, no API key, no network. The whole model is a folder you can copy.
  • It survives model churn — the API vendors change and deprecate; the exported classifier keeps working unchanged.
  • It transfers to other agents — the same pipeline reads a second agent's transcripts; only a small adapter differs.
  • It is auditable — every prediction can be traced back to the exact turn and view it came from.
"Dimension" — how we get more than labels

The same pipeline classifies more than one thing about a turn: which workflow, and (separately) how much domain knowledge it assumed, on an ordered scale. Each is a "dimension" with its own small model, sharing one encoder. Adding a dimension is a config change, not a rewrite.

The honest summary

The plumbing is proven end to end. What is not proven is that distillation beats the alternatives on real data — because no corpus we have yet is hard enough to tell the difference. That is the next measurement, and it needs real transcripts, not synthetic ones.

Your agent already writes down everything you do. This turns those logs into a small, local, auditable model that can say what kind of work each piece of it was — and it never phones home.
